# Consumer Agent Skills — Build Tasks

Companion to [`spec-skills-consumer.md`](./spec-skills-consumer.md), the same way [`tasks-components.md`](./tasks-components.md) is companion to `spec-components.md`. Every checkbox below is otherwise prospective, not retrospective — check off as completed and leave notes inline where a task surfaces a decision or a bug, the same convention `tasks.md`/`tasks-components.md` use throughout. Phase 1 builds two of the smallest, most-precedented new skills first to confirm `spec-skills-consumer.md`'s design holds up against a real skill build before the riskier and larger items later in the plan; only after that does the work move on.

**Starting state, for context:** `tm-forum-oda-consumer` ships 9 skills today (root [`README.md`](../README.md)'s Consumer table). `spec-skills-consumer.md` reviewed that set against outside input and settled on a concrete plan: 6 new skills authored from scratch (§7.1-§7.6), 1 orchestration skill (§7.7), and (originally) 2 skills vendored and adapted from existing TM Forum repositories (§7.8-§7.9) — plus a small number of blocking decisions the spec deliberately left open (§11) rather than guessing at. Phase 0 below has since resolved those decisions: `implement-oda-canvas-operator` (§7.9) is deferred out of scope entirely (0.2), and `implement-oda-component` (§7.8) is real but blocked on an unresolved source-repo license (0.1) — so this plan now targets 6 new skills, 1 orchestration skill, and 1 vendored skill pending that license. This file is about building that plan, not re-litigating it — a task here that disagrees with the spec should update the spec first, the same discipline `tasks-components.md`'s Phase 3 used when it corrected `spec-components.md` itself mid-build.

**Every new/vendored skill's `SKILL.md` must state the `spec-skills-consumer.md` §5 "ODA-first, not ODA-only" policy explicitly**, per the spec's own requirement (§7's opening line) — not inherited implicitly from this file, checked per skill below.

## Phase 2 — Build: `generate-implementation-scaffold-from-usecase` (§7.3)

Its own phase, not batched with Phase 1 or Phase 3, because `spec-skills-consumer.md` §11 explicitly flags it as "the one from-scratch proposal here without a precedent already in this corpus" and recommends a narrower pilot before committing to final scope — the same reasoning `spec.md`'s own Phase 1 gave for piloting the whole knowledge-base layout against `TMFC039` alone before batching.

- [x] **2.1** Wrote `skills/generate-implementation-scaffold-from-usecase/SKILL.md` per §7.3's spec: typed models + route/handler stubs from a linked API's cached OpenAPI schema, `TODO` markers at every domain-logic point, `oda-integration-adapter` folded in as an explicit Step 4 mode for non-ODA target interfaces. Also states explicitly (in "What this skill answers") how it differs from `implement-oda-component` (§7.8) so a caller isn't left guessing which of the two Build-stage options to use.
- [x] **2.2** Piloted against `TMFS020` (Multi Domain B2B2X Contract Management — chosen for having exactly one linked API, `TMF679` Product Offering Qualification, keeping the pilot focused) targeting Python/FastAPI/Pydantic (one concrete language, as instructed). Actually generated `models.py` (9 typed models: the resource, its `_Create` and `_Update` variants, and 6 one-level `$ref` expansions) and `routes.py` (5 handler stubs covering the schema's full `get`/`post`/`get-by-id`/`patch`/`delete` set) to a scratch directory — not committed to the repo, this is a pilot exercise, not a shipped example. Verified, not just eyeballed: both files pass `ast.parse`; `models.py` actually imports under a real `pydantic==2.11.3` and instantiates/serializes with field names matching the schema's aliases exactly; `ProductOfferingQualification.model_validate()` was run against a real cached sample to check field-level correctness, which is what surfaced the finding below.
- [x] **2.3** Real findings recorded, each folded back into the skill immediately, not just noted for later:
  - **`$ref` recursion needs an explicit bound.** `TMF679`'s own schema has a `$ref` (`ProductOfferingQualificationItem`) that itself references seven further schemas. Without a stated rule, "expand every `$ref`" is either unbounded (scope creep) or arbitrary (inconsistent runs). Added: expand one level (TM Forum's common flat `{Name}Ref` pattern justifies this), stop and placeholder-type anything deeper, always naming the unexpanded schema.
  - **`_Create` and `_Update` are two distinct schemas, not one narrower "input" type.** Caught only by reading the PATCH operation's own body `$ref` directly (`ProductOfferingQualification_Update`) instead of assuming the already-known `_Create` schema covered both — it doesn't; `_Update` adds fields (`state`, `qualificationResult`) `_Create` genuinely lacks. Original SKILL.md wording was loose enough to read as one combined variant; tightened.
  - **Major finding, not anticipated going in: a cached sample can be a different schema version than the schema it sits next to.** `TMF679`'s schema is cached at `v4.0.0`; every file under its `samples/` is v5-shaped (v5 `href`s, v5 subclassed `@type`s like `CheckProductOfferingQualification`, and field names — `expectedQualificationCompletionDate`, `checkProductOfferingQualificationItem`, a `provideResultReason` field with no v4 equivalent at all — the v4 schema doesn't define). Confirmed by literally validating a real sample against the schema-derived model: 5 fields silently vanished (Pydantic's default behavior on an unrecognized field is to drop it, not error) rather than raising anything that would have caught this by accident. Added a required schema-vs-sample cross-check to Step 3 before any sample is cited, and corrected the pilot's own `routes.py` docstrings to flag the mismatch explicitly rather than cite the samples as reliable, once found.
  - Also caught along the way: `DELETE` operations have no request-body sample by design (no body to sample), and a `...DeleteEvent_request...` file that does exist next to one is the *event-notification* payload for that lifecycle transition, not a delete-request sample — a distinct, easy thing to conflate.
  No scope-narrowing was needed — the skill's original remit (scaffolding, not business logic; language-agnostic; coexisting with `implement-oda-component`) held up under a real pilot. `spec-skills-consumer.md` §7.3 updated with the sample/schema version-mismatch finding (flagged as possibly affecting `generate-api-mocks-from-usecase`/§7.4 too, not audited here — new §11 open question) and §11's stale "worth a pilot" note resolved.
