# Consumer Agent Skills — Build Tasks

Companion to [`spec-skills-consumer.md`](./spec-skills-consumer.md), the same way [`tasks-components.md`](./tasks-components.md) is companion to `spec-components.md`. Nothing in this file has been started — every checkbox below is prospective, not retrospective; check off as completed and leave notes inline where a task surfaces a decision or a bug, the same convention `tasks.md`/`tasks-components.md` use throughout. Phase 1 builds two of the smallest, most-precedented new skills first to confirm `spec-skills-consumer.md`'s design holds up against a real skill build before the riskier and larger items later in the plan; only after that does the work move on.

**Starting state, for context:** `tm-forum-oda-consumer` ships 9 skills today (root [`README.md`](../README.md)'s Consumer table). `spec-skills-consumer.md` reviewed that set against outside input and settled on a concrete plan: 6 new skills authored from scratch (§7.1-§7.6), 1 orchestration skill (§7.7), and 2 skills vendored and adapted from existing TM Forum repositories (§7.8-§7.9) — plus a small number of blocking decisions the spec deliberately left open (§11) rather than guessing at. This file is about building that plan, not re-litigating it — a task here that disagrees with the spec should update the spec first, the same discipline `tasks-components.md`'s Phase 3 used when it corrected `spec-components.md` itself mid-build.

**Every new/vendored skill's `SKILL.md` must state the `spec-skills-consumer.md` §5 "ODA-first, not ODA-only" policy explicitly**, per the spec's own requirement (§7's opening line) — not inherited implicitly from this file, checked per skill below.

## Phase 1 — Pilot: two Discover/Design skills

`decompose-requirement-against-oda` (§7.1) and `draft-event-design-for-component` (§7.2) — both single-input, reasoning-only skills with a close existing sibling (`recommend-oda-components-for-requirement`, and every cached `component.yaml`'s own `eventNotification` shape, respectively). Built first because they're the lowest-risk new skills in the plan, to validate the general new-skill-authoring approach (structure, citation discipline, "ODA-first" statement) before Phase 2's higher-risk build.

- [ ] **1.1** Write `skills/decompose-requirement-against-oda/SKILL.md` per §7.1's spec: given a plain-language requirement with no close use-case match, produce the `business_intent`/`candidate_processes`/`candidate_components`/`candidate_apis`/`information_entities`/`questions` structure, cross-checking `information_entities` against every candidate component's own `componentMetadata.SIDs` for likely duplication (the narrowed slice of `oda-information-modeler` §6 approved). Cross-reference `recommend-oda-components-for-requirement` (run first) and `harvest-gaps-from-lessons-learned`/`propose-component-or-api-extension` (the Creator-side handoff) explicitly in the skill's own text, not just in this task file.
- [ ] **1.2** Pilot it against a real requirement that `recommend-oda-components-for-requirement` would genuinely come up empty on (find or construct one — check `knowledge/index/gaps-backlog.md` for a live candidate first, since a genuine capability gap is exactly the "nothing matches closely" case this skill exists for). Confirm every `candidate_components`/`candidate_apis` entry cited is a real id from `knowledge/index/{components,apis}.json`, never invented, and that a genuine ambiguity actually lands in `questions` rather than being silently resolved.
- [ ] **1.3** Write `skills/draft-event-design-for-component/SKILL.md` per §7.2's spec. Cite at least one real component's cached `eventNotification` block as the structural precedent in the skill's own instructions, not just describe the shape abstractly.
- [ ] **1.4** Pilot it against a real `TMFCxxx` id that has both `exposedAPIs` and an existing `eventNotification` block, drafting one plausible new event and confirming it matches the resource-level `create`/`attributeValueChange`/`stateChange`/`delete` shape every cached component already uses.
- [ ] **1.5** Update root `README.md`'s Consumer table with both new skills (matching the existing row format exactly) and run `python tools/build_plugin.py` to confirm both appear correctly in `dist/consumer/skills/` with their `knowledge/` path references rewritten. Run `python tools/validate_envelope.py --strict` to confirm neither pilot run above left any malformed artefact behind in `knowledge/`.

## Phase 2 — Build: `generate-implementation-scaffold-from-usecase` (§7.3)

Its own phase, not batched with Phase 1 or Phase 3, because `spec-skills-consumer.md` §11 explicitly flags it as "the one from-scratch proposal here without a precedent already in this corpus" and recommends a narrower pilot before committing to final scope — the same reasoning `spec.md`'s own Phase 1 gave for piloting the whole knowledge-base layout against `TMFC039` alone before batching.

- [ ] **2.1** Write `skills/generate-implementation-scaffold-from-usecase/SKILL.md` per §7.3's spec: typed request/response models and route/handler stubs from a linked API's cached OpenAPI schema, `TODO` markers at every point real domain logic belongs, the `oda-integration-adapter` mode folded in for non-ODA target interfaces. State explicitly, in the skill's own "what this does NOT do" section, that it does not generate business logic — the schema doesn't ground that, and the skill must not imply otherwise.
- [ ] **2.2** Pilot it against one real `TMFSxxx` use case's linked APIs, in one concrete target language (pick one — don't try to stay language-agnostic in the pilot itself, only in the skill's own instructions). Check the generated models actually match every field/type in the cached schema, and that every `TODO` marker lands somewhere a real implementer would recognize as "business logic goes here," not scattered arbitrarily.
- [ ] **2.3** Record the pilot's real findings back into this task (not just "it worked") — this is exactly the scope-narrowing check §11 asked for. If the pilot surfaces that the scope needs narrowing further (or that a language-specific version is needed rather than one generic skill), update `spec-skills-consumer.md` §7.3 to reflect it before finalizing the skill.
- [ ] **2.4** Update root `README.md`'s Consumer table, rebuild `dist/`, re-run `validate_envelope.py --strict`.

- [ ] **3.2** Write `skills/audit-implementation-against-component/SKILL.md` per §7.5's spec — Core Function (`coreFunction.exposedAPIs`/`dependentAPIs`) and Supporting Function (`managementFunction`/`securityFunction`) conformance reported as two separate dimensions, never blended into one score.
