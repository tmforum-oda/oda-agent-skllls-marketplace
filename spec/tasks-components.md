# Component Specification PDFs — Build Tasks

Companion to [`spec-components.md`](./spec-components.md), the same way [`tasks.md`](./tasks.md) is companion to `spec.md`. Phase 1 processes exactly one component end-to-end to confirm `spec-components.md`'s assumptions hold against a real file before committing to them at scale; only after that does the work move to batches of 5. Check off as completed; leave notes inline where a task surfaces a decision or a bug, the same convention `tasks.md` uses throughout.

**Media processing is part of each component's own processing step, not a later pass.** Every phase from Phase 1 onward ends with running `skills/process-component-media` for each component it just converted, **dispatched to a sub-agent** (one `Agent` call per component, `subagent_type: general-purpose` — the skill's own multimodal image-reading and PlantUML-authoring work has no business bloating the main conversation's context, the same reasoning `spec.md` §12 gives for keeping `process-usecase-media`'s output out of a skill's own steady-state context). Each sub-agent is given the component id and told to invoke the skill and report back what it classified/renamed/wrote — the main thread reviews that report, it doesn't do the image reading itself.

**Starting state, for context:** 31 component folders already exist under `knowledge/components/` (from `spec.md` Phase 2/4 — `component.yaml` + `component.meta.json` only). `spec-components.md`'s survey (§6) already determined, for all 31, which have a fetchable PDF specification (25), which don't (6), and — for the 25 — the exact discovered URL, PDF version, and cached-YAML version. That survey work is **not** repeated here; this file is about fetching and converting, not re-discovering.

**Revision note:** Phase 1 was built and reviewed once already, then rebuilt from scratch after user review rejected the first version's table handling (real tables were being flattened into fenced code blocks of raw text instead of proper Markdown tables). Batches 1–2 (Phases 2–3 below) had already been run against the first version before that review landed; both were fully reverted (`references/components/` and every `TMFCxxx.md`/`media/` except `TMFC039`'s, deleted) so nothing downstream would depend on output the redo would invalidate. Phase 0/1 below describe the *current*, table-rewritten tool and its validation — the reverted first attempt isn't documented here since it no longer reflects what the tool does.

## Phase 0 — Tooling

- [x] **0.1** Confirmed the discovery mechanism from `spec-components.md` §3 cannot be scripted with a plain HTTP fetch: `curl`-ing a component's directory page (`https://www.tmforum.org/oda/directory/components-map/x/TMFC039`) returns a 5.5KB client-rendered SPA shell with no PDF link anywhere in the raw HTML — the link only exists after the page's JS runs. Confirmed by diffing that raw fetch against the same page read through an actual browser session, which does surface the real S3 link in the rendered DOM. This means the discovery step genuinely requires a driven browser (or reverse-engineering the SPA's backing API, not attempted — out of scope, matching `spec.md`'s general preference for not pre-building automation a v1 pass doesn't need yet), not just a URL-construction script.
- [x] **0.2** Wrote `tools/pdf2md_component.py` (see its own docstring for the full design rationale). Key decisions, each validated against a real document before being treated as settled:
  - **Tables are real GFM Markdown tables, extracted structurally, not read off as text.** `pdfplumber`'s `find_tables()` does its own line/rect-based structural detection and returns each table's bounding box plus its actual cell grid directly — this isn't a text-layout heuristic (a spacing-heuristic version was tried first and rejected on review: it rendered every table as a verbatim fenced code block of raw column-aligned text, which is what this rewrite replaced). `page.filter()` then extracts the surrounding *prose* text with every table's bounding box excluded, so table content is never duplicated into the prose stream.
  - **A table that continues onto the next page is merged into one continuous table, not emitted as several.** TM Forum's own template re-states each table's header row on every new page. The new page's header is compared against the still-open table's using a "compatible" match (one being a prefix of the other counts as equal, not just exact string equality) rather than requiring the two to be byte-identical, and — deliberately — only the *first* header seen is ever kept, never a later one, because:
  - **A wrapped data row straddling a page break can bleed leftover body text into the next page's restated header row.** Confirmed on `TMFC039`'s Functional Framework Functions table: "Function Description" arrives on the second page as "Function Description or group of products of the partner." (the tail end of the previous page's last row). Always keeping the first (clean) header rather than whichever one a given page happens to show avoids ever displaying the corrupted version.
  - **A single-column table has to be filtered out *before* it touches the open-table state, not just before being emitted.** `find_tables()` occasionally detects a stray one-cell fragment of wrapped text as its own tiny "table" alongside a real one on the same page (confirmed: a spurious `["Function"]` table next to the real 9-column one, on every page of the Functional Framework Functions section). It's never emitted either way (a real table needs ≥2 columns to render as one), but if it isn't skipped *before* the merge-or-start-new decision, it still resets the open table as a side effect — which was silently defeating the cross-page merge above on every single page until this was caught.
  - **Prose and tables are interleaved in true top-to-bottom reading order, not "all of a page's prose, then all its tables."** A table and a section-transition heading can share one page (confirmed: `TMFC039`'s own "3.1 Exposed APIs" continuation table and the "3.2 Dependent APIs" heading both fall on the same page) — processing every page's prose in one pass and its tables in a separate pass afterward silently attached the *first* table to the *second* heading's section. Fixed by slicing each page at each table's own vertical extent and processing prose → table → prose → table … in that order, using `pdfplumber`'s `within_bbox` to crop the prose text to just the region above/between/below the tables.
  - **Header-row merging.** A table's header can itself be split across more than one grid row (a merged/split header cell rendering as an extra row underneath, e.g. "Mandatory /" on one row and "Optional" directly below it in the same column) — detected as any leading row whose first cell is empty, merged column-wise into one real header before any data rows are read.
  - **Heading detection is a numbered-heading regex** (`2.3. Functional Framework Functions`), not font-size/style metadata — these PDFs carry none that `pypdf`/`pdfplumber` can read. Real generalization bugs found and fixed while validating against more than one document's actual structure:
    - A Table-of-Contents entry has the exact same numbered-heading shape as a real heading, and the *only* textual difference is the dot-leader (`....... 5`) — filtered out before heading detection ever sees it, or the ToC's own "1. Overview" line matches as the first heading instead of the real one.
    - Not every component numbers "Overview" as section "1." — `TMFC006` numbers its Table of Contents "1." and Overview "2." — so the "skip until the first real heading" gate matches on the *title text* ("overview"), not a hardcoded number.
    - A component's References section can contain its own independently-numbered list (`TMFC006` cites "1. IG1228…" / "2. TMF633…" as plain enumerated items, textually indistinguishable from real top-level headings) — without a fix, such a line can look like it legitimately ends an active drop scope early. Fixed by tracking the highest top-level section number legitimately seen so far and refusing to treat a same-or-lower-numbered top-level line as a real heading at all.
  - **Boilerplate exclusion set matches `spec-components.md` §4.1 exactly**: title/cover page (everything before the real "Overview" heading), Notice, Table of Contents, References (and children), Administrative Appendix (and children: Document History/Version History/Release History/Acknowledgments).
  - **Images are deduplicated by content hash, with a byte-size floor on top.** Every page of these PDFs repeats the same TM Forum logo. Hash-dedup alone still let through both of the logo's colour variants (kept on their first occurrence each); a 15KB floor (real diagrams ran 26KB+, the two logo bitmaps 9.0–9.2KB) removes them entirely.
  - **Known, accepted limitation, not fixed:** a heading whose own title genuinely wraps onto a second physical line (confirmed on `TMFC039`'s own section 2, "eTOM Processes, SID Data Entities and" / "Functional Framework Functions") is *not* merged back into one line — an earlier attempt at this (matching any short non-heading line immediately following a heading) also merged unrelated short sentences into heading titles (confirmed corrupting `TMFC006`'s "SID ABEs" heading with "SID ABEs this component is responsible for are:"), which is a worse failure than a heading rendering on two lines. All of the wrapped title's actual words are still present as an ordinary paragraph immediately below the (shorter) heading — nothing is lost, it just isn't recombined into one line.
  - **Images are linked inline from the body (`![](media/imageNN.png)`), at the position they actually appear — not just extracted to `media/` and left unlinked.** First version extracted the files correctly but only appended a trailing "(N diagrams extracted, unprocessed)" footnote with no actual link — caught on user review of Phase 1's output. Fixed by folding images into the same top-to-bottom interleaving pass as tables (sorted alongside them by vertical position on the page, per the bullet above), so an image lands in the body right next to the sentence that introduces it. `pdfplumber`'s `page.images` supplies each image's position; `pypdf`'s `page.images[i].data` supplies the already-decoded bytes (`pdfplumber`'s own image objects are a raw, still-encoded stream) — matched up by index within a page, confirmed reliable by checking both libraries report the same count and order per page on the real file.
  - **A blank-header column's data lands one column away from where its header actually is, and only for columns whose header itself needed the row-merge above.** Caught on user review: the SID ABEs table rendered with 6 columns for what is visibly a 4-column table in the source PDF. Every column whose header text is tall enough to wrap across the header's own multiple grid rows (e.g. "SID ABE" + "Level 1" on two rows) throws off `pdfplumber`'s column-boundary detection for the *data* rows beneath it — that data lands one column to the left of its real header instead. Confirmed against every table in the document, not just this one: `TMFC039`'s Overview table, Exposed/Dependent APIs tables, and Version/Release History tables all show the identical pattern, and every column whose header *didn't* need a row-merge is already correctly aligned. Fixed by recording exactly which column indices received a header merge, then shifting only those columns' data back one position before reading it — not a blanket "any blank-header column merges into its neighbour" rule, which would also fire on genuine, always-empty spacer columns that don't need touching.
  - **A leftover wrapped line from the previous page's last row can be mistaken for a real header-continuation row**, corrupting a *different*, unrelated bug fix in the process. Confirmed on the Functional Framework Functions table: page 2 opens with `['', '', 'or group of products of the partner.', '', ...]` — the tail end of a Description cell that didn't fit on page 1, with an empty first cell just like a genuine continuation row. Two compounding failures from treating it as one: the header got corrupted (already handled — the caller always keeps the *first* header seen, see above) and, found only after that fix, this row's own non-empty cell got marked as a "shifted" column exactly like the bullet above, so a later legitimate data row's Function Name was wrongly merged into Function Description on every subsequent row. Fixed by requiring every non-empty cell in a candidate continuation row to look like an actual header label (short, no sentence-ending punctuation) before accepting the whole row as a continuation — a real fragment ("Function", "Level 1", "(or set of BEs)") always does; a leftover wrapped sentence never does. The row itself, now correctly rejected as a continuation, still needed a second small filter (drop any "data" row with fewer than two populated cells) so it doesn't show up as a near-blank junk row instead.
  - **A logo image being filtered out (too small, already seen) must not still close the currently-open table.** `process_image()` was calling `flush_table()` unconditionally before checking whether the image actually survived the dedup/size filter — since every page carries two such logo images, this was silently fragmenting the Functional Framework Functions table back into one piece per page again, and would have looked like a regression of the already-fixed cross-page-merge bug above. Found by checking *why* the merge broke again after the two bullets above landed, not by assuming those two fixes were the only things that could have caused it. Fixed by calling `save_image()` first and only touching para/table flush state if it actually returns a filename.

This is the most consequential finding of the whole effort so far: prior review passes read the *shape* of the output (does it look like a well-formed table? is the prose in a plausible place?) without independently cross-checking every table's row count and every paragraph's position against the raw PDF grid, which is exactly what let all four bugs through undetected.
  - **A table with only 1–2 real (non-blank-header) columns can have a perfectly legitimate data row that populates just one of them, and the existing "≥2 populated cells drops a leftover fragment row" filter (Phase 0.2) was deleting that entire row down to zero, which silently dropped the *whole table*** (`flush_table()` only emits a table with ≥1 data row). Confirmed on `TMFC008`'s SID ABEs table: source has one real row (`Service ABE | ` with SID ABE Level 2 blank), rendered as no table at all. Fixed by scaling the threshold to the header's own real (non-blank) column count — `min_populated = 1 if len(real header columns) <= 2 else 2` — rather than a hardcoded 2, so the filter still catches genuine wide-table leftover fragments (the case it was built for) without misfiring on narrow, legitimately-sparse tables.
  - **A single-row header whose own label text is split across grid columns pdfplumber doesn't align with the data row beneath it** — a *new* variant of Phase 0.2's already-fixed "blank-header column data lands one column left" bug, this time with no second header-continuation row at all to hang the fix on (the existing fix only tracks `shifted_cols` from an actual multi-row header merge). Confirmed on the same `TMFC008` table (`header=['', 'SID ABE Level 1', '', '', 'SID ABE Level 2 ...', '']`, `data=['Service ABE', None, None, ...]` — label at columns {1,4}, value at column {0}) and, far more consequentially, on **`TMFC003`'s Exposed APIs table**, where this exact misalignment on a 15-column raw grid caused every row to render with 5 spurious blank spacer columns interleaved with the 5 real ones (`|   | API ID |   | API Name |   | ...`) in the *already-committed* Phase 2 output. Fixed with a general, shape-based rule: if a data row's populated column indices share nothing with the header's populated column indices, but shifting every one of them right by exactly one column makes them line up exactly with populated header columns, apply that shift.
