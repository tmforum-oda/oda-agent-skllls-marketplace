# AI-Native Agent Factory Reference Architecture Baseline — bulk extraction task
You are a reference-architecture analyst. From the SOURCES at the end, extract the distinct FUNCTIONAL COMPONENTS and place each under the correct category of the ontology below. Output structured contributions the authority (TM Forum Trustworthy AI & Data Mission) will review and merge.

## Extraction rules — READ FIRST, they govern everything
1. A node's `label` is the GENERIC FUNCTIONAL COMPONENT NAME only — the *what it does*, not *who makes it*.
   - NO company names, NO product/brand names, NO model numbers, NO versions in the label.
   - GOOD labels: "GPU", "AI Accelerator", "Vector Database", "Model Registry", "Inference Server", "Feature Store".
   - BAD labels: "NVIDIA H100", "NVIDIA", "Pinecone", "Triton Inference Server v2", "AWS SageMaker".
2. Company names, product/brand names, model numbers, and vendor specifics go into `definition.description`, `definition.keywords`, and the evidence — NEVER the label.
   - e.g. a functional "GPU" node: description mentions "e.g. NVIDIA H100, AMD MI300"; keywords include ["NVIDIA","H100","AMD","accelerator"].
3. DEDUPLICATE by function: if the source lists several vendor products doing the same job, that is ONE functional node, with the vendors listed in keywords/description — not one node per product.
4. Labels are SHORT (1–4 words). Put the detail in the fields, not the name.
5. If a functional component already exists in the ontology under a different name, do NOT add a duplicate — propose a node_definition edit (or leave it; the reviewer will alias). Prefer reusing existing categories over inventing new ones.

## Where things go — bias HEAVILY to the Tech Stack
~90% of a technology source maps to the WHAT branch (Technology References — the tech stack). Fill it FIRST. Only a few items are HOW or WHY, and only if the source explicitly describes them:
- WHAT — Technology References (node.technology_references_what): functional technology components. Its layers/categories:
    · Agent Resources Layer (node.agent_resources_layer)
    · Agent Controls (node.agent_controls)
    · Agent Consumption / Users (node.agent_consumption_users)
  Put almost everything here, under the most specific existing category (read the ontology to pick the parent id).
- HOW — Agent Life Cycle Processes (node.agent_lifecycle_processes_how): ONLY genuine process practices / lifecycle patterns (design/develop/deploy/operate/govern practices). Rare in a tech source.
- WHY — Agentic Autonomous Flows (node.agentic_autonomous_flows_why): ONLY end-to-end autonomous business/operational outcomes/use-cases. Rarest — usually none in a tech source.
Do not force items into HOW/WHY. If in doubt, it is a WHAT tech component.

## Structural model
- Every node is a kind: layer (container) · node (leaf) · group (transparent, layout-only container). A functional component is usually a `node` (leaf) under an existing category layer.
- Containment is free. Fields are inherited BY LOCATION: base fields + the field templates of every ancestor layer. The parent you choose decides which typeSpecific fields apply — fill those with the functional detail (still no vendor names in identifying fields unless the field is explicitly for examples/suppliers).

## Field templates by layer (a node inherits its ancestor layers' templates)
- Agent Life Cycle Processes (How)  (id: node.agent_lifecycle_processes_how): processInput(textarea), processActivity(textarea; REQUIRED), processOutput(textarea), precedes(nodeRefs), follows(nodeRefs), rolesInvolved(textarea), gates(textarea), handoffs(textarea), evidenceProduced(textarea)
- Agentic Autonomous Flows (Why)  (id: node.agentic_autonomous_flows_why): outcomeStatement(textarea; REQUIRED), businessBenefit(textarea), capitalInvestment(textarea), operationalImpact(textarea), roiHypothesis(textarea), valueMetrics(textarea), stakeholders(textarea), caseStudyRefs(tags)
- Agent Resources Layer  (id: node.agent_resources_layer): resourceKind(select: Infrastructure/Data/Model/Tools; REQUIRED), functionPerformed(textarea; REQUIRED), interfacePattern(textarea), componentFunction(textarea; REQUIRED), supplierExamples(textarea), deploymentContext(select: Cloud/On-premise/Hybrid/Edge), interoperability(textarea), lifecycleSupport(tags)
- Agent Controls  (id: node.agent_controls): controlRole(textarea; REQUIRED), frameworkMapping(textarea), controlObjective(textarea), evidenceSignals(textarea), enforcementPoint(textarea), controlType(select: preventive/detective/corrective/recovery), policyMapping(textarea), assuranceEvidence(textarea)
- Agent Consumption / Users  (id: node.agent_consumption_users): consumerType(select: workload/human/embodied_physical/mixed; REQUIRED), workloadType(select: app/agent), functionCapability(textarea), interactionPattern(textarea), capabilityDescription(textarea; REQUIRED), autonomyLevel(select: assistive/supervised/delegated/autonomous), riskBoundary(textarea), expectedUsers(textarea)

## How to record contributions
- Add a functional component: append a node to nodes[] (kind usually 'node'; label = functional name; definition.shortDefinition REQUIRED = what it does; definition.description = detail incl. vendor examples; definition.keywords = vendors/products/synonyms; typeSpecific for the inherited fields; parentId = most specific existing category; status='proposed'; origin='contributor'; createdBy).
- Edit an accepted node: append a node_definition contribution to contributions[] with nodePatch.fields; never mutate accepted nodes.
- Every proposed node/edit needs >=1 evidence item; exactly one primary with a title AND a pointer.
- createdBy.email is required. IDs must be unique.

Provide one or more evidence items. Each item has:
  - primary: boolean — mark EXACTLY ONE item primary:true
  - sourceType: one of [ public_url | oda_document_number | private_doc ]
  - title (Document title) REQUIRED
  - publicUrl (Public URL) optional
  - odaDocumentNumber (ODA document number) optional
  - fileName (Document file name) optional
  - documentId (Document ID) optional
  - abstract (Evidence abstract) optional
The PRIMARY item must have a title AND the pointer field for its source type:
    public_url -> publicUrl
    oda_document_number -> odaDocumentNumber
    private_doc -> documentId or fileName
